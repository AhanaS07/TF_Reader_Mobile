## 3. DOM inspection

Do this **before** the screen-reader runs — it explains most of what follows.

Done via Chrome DevTools Protocol over `adb forward` to the WebView's debug socket (`chrome://inspect`
equivalent, scripted directly rather than through the Chrome UI) against the pre-existing book noted
above §4/§8 - not yet repeated against Sample A/B.

| Check | Finding |
|---|---|
| Content inside an iframe / content document? | **Yes.** `document.querySelector('iframe')` finds one `epubjs-view-*` iframe; `contentDocument` was accessible (same-origin) and queryable. |
| Do `h1`/`h2` survive rendering? | Partial data: the specific page inspected had 1 real `<h2>` ("REFERENCES") and 0 `<h1>` - consistent with a references/back-matter page, not conclusive for the whole book. Needs a chapter-start page to confirm `<h1>` survival. |
| Are paragraphs real `<p>` elements? | **Yes** - 141 real `<p>` elements found in the inspected page's content document. |
| Does pagination rewrite or clone the DOM? | Not fully determined. The iframe reports as very wide (~12,741px) with `overflow: hidden`, consistent with epub.js's standard CSS-multi-column continuous layout (one DOM, scrolled/clipped per page) rather than per-page DOM cloning - but this is inferred from the iframe's computed style, not directly confirmed against pagination events. |
| Are off-screen pages hidden from the a11y tree? | **No, but not correctly exposed either** - see F6. Off-screen/off-column content nodes are present in the native accessibility tree (not excluded), but the large majority report degenerate `bounds="[0,0][0,0]"` rather than being hidden or correctly positioned. |
| Any `aria-hidden` applied by the library itself? | **None found** - `document.querySelectorAll('[aria-hidden]').length` was 0 in the inspected content document. |
| Are images preserved with their `alt` attributes? | All 7 `<img>` elements in the inspected page had an `alt` attribute present, but every one was an **empty string** (`alt=""`) - either all genuinely decorative, or meaningful alt text was stripped/never authored; not distinguishable from the DOM alone. |
| Are internal links real `<a href>` elements? | **Yes** - 32 real `<a>` elements found (citation/cross-reference links, per the `uiautomator` dump's `[1]`, `[2]`, "Figure 1" etc. entries in F6). |

The off-screen-page question is the likely root cause if page changes misbehave: if
neighbouring pages stay in the tree, the screen reader will read content the user
cannot see.

## 8. Findings

> One numbered finding per real observation, with the layer it belongs to —
> `epub.js`, our WebView glue, native RN, or the EPUB source itself.

```text
F1. [native RN] Contents/TOC toggle announces as "Contents quantity 22, double tap to activate" on
    TalkBack (Android, pre-existing book) - confusing, not a clean announcement of what the control
    does or what "22" refers to (likely the visible "Contents (22)" label text, with the parenthetical
    number read oddly rather than as a normal quantity/count). Matches the pre-spike code audit's
    flag that this button has no explicit `accessibilityLabel`.
F2. [native RN, positive] The TTS toggle button correctly announces its on/off state via
    `accessibilityState` - "TTS off, button" when off, and after activating, the control reads back
    with selected/unselected state ("TTS on, selected" / "TTS off, unselected"). Android, pre-existing
    book.
F3. [native RN, positive] Previous/Next-page and Search buttons all announce cleanly and
    unambiguously on TalkBack (Android, pre-existing book) - "Previous button, disabled" (correctly
    reflects the greyed-out state on page 1, despite relying on RN's plain `disabled` prop rather than
    an explicit `accessibilityState` in the source), "Next button, double tap to activate", "Search
    this book button, double tap to activate".
F4. [layer TBD - needs epub.js/WebView-glue code review to attribute] **The core finding of this
    spike.** On Android/TalkBack, the WebView's rendered book content is unreachable through every
    live interaction method tested - linear swipe navigation, direct touch exploration on visible
    paragraph text, and a third, targeted touch aimed specifically at a screen region a `uiautomator`
    dump confirmed has a real, non-degenerate accessibility node (see F6). All three were silent. This
    is a confirmed, practical, total FAIL for screen-reader usability of book content on Android,
    independent of the deeper mechanism explored in F6. Not yet attributed to `epub.js`, the WebView
    glue, or the Android WebView's own accessibility bridge, pending further DOM/code inspection.
F5. [native RN, likely a distinct bug from F4] After the TOC panel is used to navigate to a chapter
    (confirmed: panel visually closes, new chapter content displays underneath), TalkBack swipe
    navigation still reaches elements ("Navigation", "Close button") that appear to belong to the
    now-closed TOC panel, immediately after which nothing further is reachable. This suggests the
    TOC panel's elements are not being removed from the accessibility tree when it closes (missing
    `accessibilityElementsHidden`/`importantForAccessibility="no-hide-descendants"` equivalent to
    what `ReaderScreen.tsx` already applies to the swipe-catcher and privacy-cover overlays), separate
    from F4's WebView-content problem.
F6. [likely epub.js, pending confirmation] `adb shell uiautomator dump` was used to inspect the raw
    Android accessibility node tree directly (independent of live TalkBack interaction). It shows the
    WebView's DOM content IS present as native accessibility nodes - full paragraph text, headings,
    and even individual citation links ("[1]", "Figure 1", etc.) all appear with correct text. BUT the
    large majority of these nodes report a degenerate `bounds="[0,0][0,0]"` (zero width/height) -
    only a couple of nodes near the bottom of the visible viewport reported real, non-zero bounds. A
    zero-size bounding box cannot be hit by touch exploration and is a plausible root cause for F4's
    swipe/touch failures. Touching the one screen region confirmed to have a real-bounds node was
    ALSO silent (see F4), so bounds degeneracy alone does not fully explain the failure either - live
    touch-exploration routing into the WebView may be broken independently of the static node tree's
    correctness. Suspected connection to epub.js's CSS-multi-column pagination layout (the whole
    chapter is laid out as one very wide horizontal strip, per §3's pagination-DOM-rewrite question),
    but this needs code-level confirmation, not further on-device guessing.
```

Attributing the layer matters: an unnavigable chapter caused by a bad EPUB is a
content problem, the same symptom caused by `epub.js` pagination is ours to fix.

## 10. Conclusion

```text
Is the epub.js DOM usable by screen readers as-is:
  NO, on Android. The DOM itself is reasonably semantic where inspected, but TalkBack cannot reach
  any book content through swipe navigation, direct touch exploration, or targeted touch on a
  confirmed-real-bounds node - three independent methods, all silent. Native reader-toolbar controls
  (Previous/Next/Search/TOC/TTS-toggle) work correctly and are well-labelled, so the app is not
  wholly unusable, but the core reading experience is inaccessible to TalkBack users today.

Work required on our side:
  1. Root-cause why WebView content nodes report degenerate bounds=[0,0][0,0] (F6) and why even a
     node with correct bounds was unreachable by touch - likely tied to epub.js's CSS-multi-column,
     JS-driven (non-native-scroll) pagination technique interacting with Android's WebView
     accessibility bridge, but not yet confirmed at the code level.
  2. Fix the TOC panel leaving elements in the accessibility tree after chapter-selection dismissal
     (F5) - likely a missing accessibilityElementsHidden/importantForAccessibility equivalent to
     what ReaderScreen.tsx already applies to its other overlays.
  3. Give the Contents/TOC toggle an explicit, clear accessibilityLabel (F1) - cheap, independent fix.

Work that belongs to epub.js / is unfixable by us:
  Possibly the CSS-multi-column pagination technique itself, if it is fundamental to how epub.js lays
  out reflowable content - this may need an alternate rendering/pagination strategy for
  assistive-technology users rather than a small patch, but that conclusion needs code-level
  investigation (not further on-device testing) before it can be stated with confidence.

Blocking for Week 1:
  YES. This is a confirmed, total blocker for TalkBack-based reading of book content on Android -
  the single largest open risk named across every prior accessibility doc in this workstream is now
  confirmed rather than hypothetical.

Carried to Day 3:
  - iOS/VoiceOver pass (no device available for this session).
  - Re-running against the actual Sample A/B synthetic fixtures (§2) - this pass tested a real
    pre-existing book instead; worth checking whether Sample A's simpler markup (no CSS-column-heavy
    academic-PDF-derived layout) avoids the same bug, which would narrow the root cause further.
  - Remaining untested matrix rows: TTS Play/Pause (inside the TTS panel), Bookmark, Settings, large
    text, high contrast, and the TOC modal focus-trap question (can focus "escape" the panel while
    open?).
  - Code-level root-cause investigation into epub.js's pagination technique vs. Android's WebView
    accessibility bounds computation (F6), to move F4 from "confirmed symptom" to "attributed layer
    and fix."
```
