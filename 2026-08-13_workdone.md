## base64.ts performance fix (user-found issue)
User flagged `bytesToBase64` (base64.ts:13-26) as a naive per-3-byte loop with string concatenation, worried about a ~20MB book producing ~7M iterations / ~27MB output string.

Investigated real impact first: this isn't just readerAssets.ts's WebView bridge — aesGcm.ts round-trips the FULL book through bytesToBase64/base64ToBytes on every encrypt/decrypt call too (the native crypto module's bridge takes base64 strings), so a real "open a book" flow hits this ~3 times.

Wrote a dedicated base64.test.ts (didn't exist before) cross-checking byte-for-byte against Node's own Buffer, including the 0-300 length range the file's header had always claimed to verify but never actually committed as a test.

Rewrote both encode and decode, first pass. Initial Node-only benchmarking looked dramatic (17s -> ms) but that turned out to be almost entirely a Jest `toEqual`-on-large-typed-arrays artifact, not real function performance — fixed the test to use a fast manual byte-compare instead of `toEqual` for large payloads.

**Critical finding from real on-device testing (not just Node):** temporarily instrumented App.tsx with a timing useEffect (reverted after), ran on both the iOS simulator and Android emulator with a real 20MB payload. Real Hermes results:
- decode (indexOf scan -> O(1) lookup table): iOS ~3.0s -> ~2.0s, Android ~3.1s -> ~1.7s. Real, consistent win on both platforms.
- encode (concat loop -> chunked fill+join): iOS 1.9s -> 2.8s (WORSE), Android 1.7s -> 2.4s (WORSE). A second alternative (array+join, no chunking) also didn't beat the original on Android.

Node/V8 benchmarks were not a reliable proxy for Hermes here — the two engines disagreed about which encode version was faster. Shipped only the validated fix: decode's lookup table. Encode is unchanged from the original algorithm, with a header comment explaining why (measured, not assumed) and warning against re-"optimizing" it without a fresh on-device benchmark.

Full regression: typecheck clean, lint clean, 31 suites / 276 tests pass. Re-verified the actual Reader still renders on both platforms after reverting the instrumentation. Dispatched a verification agent for a final adversarial review before calling this done.

**Verification agent verdict: PASS, no issues.** Confirmed independently: `bytesToBase64` is byte-for-byte untouched from the original commit (zero diff in the function body); the `REVERSE` lookup table is exactly equivalent to the old `indexOf` including the out-of-range/error-message behavior; base64.test.ts genuinely cross-checks against Node's Buffer rather than self-round-tripping (rules out "both functions wrong the same way"); all real call sites (aesGcm.ts, keyStorage.ts, deviceKeypair.ts, deviceKeyRegistration.ts, readerAssets.ts) checked, including that aesGcm.ts passes `.subarray()` views into bytesToBase64 in production and that's unaffected; no leftover App.tsx instrumentation. Re-ran typecheck/lint/full suite independently: all clean, 31/276.

Status: done. base64.ts's decode path is measurably faster on real devices (not just claimed); encode is intentionally unchanged, backed by on-device evidence rather than assumption.

## flambeau real-backend contract review

Read the full flambeau OpenAPI spec end to end and compared it against our DRAFT `content-licence.ts`, writing the comparison to `flambeau-contract-comparison.md` (no code changed for this — explicitly a decision doc, not a plan). Headline finding, and the direct answer to "does access get re-verified": the real backend re-checks entitlement on **every book open** via `POST /api/v1/reading-sessions` (~5 min grant) — "a subscription can lapse between borrow and read" — and we have no equivalent anywhere; a book already on disk is never re-checked after its initial download. Other real divergences: no `checksum` field exists server-side (GCM's tag is the integrity guarantee); the real response is `sessionId`/`loanId`/`expiresAt`/`serverTime` + a structured signed-URL object, not our flat `encryptedFileUrl` string; there's no device-registration endpoint at all (device key rides every request instead — `deviceKeyRegistration.ts` is confirmed unused in the app today); and there's a whole loan/borrow layer we don't model. Verdict in the doc: merge, don't replace — adopt the real shape, but the per-open re-verification needs a call site that doesn't exist yet and crosses into Reader's (Ahana's) territory, so it's flagged rather than built.
